## Context

The Day 10 gate went live earlier the same day: the Cloud Function is deployed,
two recipient tokens are issued (`arken-web-form`, `arken-followup`), and the VM
sits stopped until someone clicks *Start*. The first real visit arrived and
**stopped at the status page** — the link was opened at 20:25 UTC and polled for
about ten minutes without the demo ever being started.

That put the next question in front of us: when a visitor does start it, what do
they do with a text box over a corpus they have never seen?

## D1 — The panel is organised around fail-closed, not around features

*Raised by Yi Xin: "我这个项目的主打亮点就是 fail-close。是否从这个方向进行设计和引导了。"*

The implementer's first pass grouped questions by capability — grounded answers,
off-corpus, wrong premise, multi-hop, figures — with the answerable group first
and the largest. Audited against the actual claim, that pass was **half right**:
6 of 12 questions expected an answer, and of the five gates the engine can refuse
at, three were exercised.

Decision: reorganise around *the families of ways a question can fail to be
answerable*, and say so in the caption. One control group of answerable
questions stays first and is cut to two — the refusals only read as a feature
if the visitor has just watched the same system answer.

Result: 14 questions, 7 groups. Two distinct fail-closed mechanisms that the
first pass missed are now covered — **the right document that simply does not
state the detail** (a different gate from "nothing scored"), and **the
no-derivation rule** (both numbers present, their sum not).

## D2 — Three things the panel must not do

Fail-closed framing creates its own temptation to overclaim. Written into the
code as constraints, and into the caption as text the visitor reads:

1. **No gate is promised.** Whether an off-corpus question stops at `threshold`
   (nothing scored above the frozen threshold, model never called) or at `llm`
   (something scored, model judged it insufficient) depends on retrieval scores
   no static table can predict. The gate name on screen *is* the answer.
2. **No retraction on demand.** `citation-validation` — text visibly withdrawn
   after streaming — is the most striking gate and is by construction
   unsummonable: it fires only when the model produces a claim it cannot ground.
   The caption says the visitor may see it and that nothing here promises it.
3. **No implied owner.** Refusal routing names an owner only for a DMC the
   package *declares missing*. Checked, not assumed: `collect_gaps` over the
   deployed corpus (package-a + package-c) returns **zero** gaps, so every
   refusal carries an `owner_reason` explaining why no owner could be named.

Every group note is phrased as a question rather than a prediction, for the same
reason Day 8 spent four rounds removing outcome claims: the generator is
non-deterministic behind deterministic gates.

## D3 — Suggested questions must come from reviewed evaluation sets

Questions invented for the screen would be marketing copy. All 14 are verbatim
rows from `eval/golden/` (day4 retrieval, day8 adversarial, day11 multi-hop,
day12 multimodal), enforced by test.

The red team then sharpened this: the first test globbed `eval/golden/*.jsonl`,
which also matches `*.candidates.jsonl` — AI-drafted rows that were never
adjudicated. The four reviewed sets are now named explicitly.

## D4 — One click must cost exactly what typing would

A button next to a question makes spending easy, so the fence had to be checked
rather than assumed. Two things came out of the review:

- Streamlit disables `st.chat_input` while a run executes but **not buttons**, so
  an impatient visitor could click through suggestions, each click aborting the
  previous run *after* its LLM call was issued and billed. A question is now
  accepted on one run and asked on the next, so the panel that renders on the
  spending run renders its buttons disabled.
- The claim "clicking equals typing" was asserted by a regex over the source.
  The query call site is now one function, `ask_backend`, and the test executes
  the shipped function against a fake transport.

Explicitly **not** solved client-side: two browser tabs on the same `?k=`. The
backend concurrency semaphore and the per-boot call cap remain the real fences,
and the code says so instead of implying otherwise.

## D5 — The gate function's memory: 256 MB → 512 MiB

*Approved by Yi Xin.* Not a design choice so much as a defect found while
reading logs for the visit record: the function was exceeding its 244 MiB usable
limit on essentially **every request** — 78 events in six hours — so each poll
killed its instance and cold-started the next. Responses were still 200, but a
`POST /api/start` killed mid-flight would have shown the visitor a dead button.

Applied and verified: revision `00003-shq` at 512 MiB, six polls, zero memory
events.

## Open items (Yi Xin's call)

- These UI changes are **not yet on the VM**: it boots from a fixed clone at
  `/opt/learnarken/LearnArken` with no pull on start, so reaching production
  means starting the VM, pulling, restarting `learnarken-demo.service`.
- The 14 questions have been verified to render, to be accepted by the backend's
  request bounds, and to come from reviewed sets — but **not** run end to end
  against the live stack. Doing so is one VM session (~$0.20, ~3 min boot).
- `DEMO_MAX_LLM_CALLS=200` per boot is unchanged. One-click asking makes the
  quota easier to spend; re-deciding the number against the $20 envelope was
  already flagged as a human call in the Day 10 red team.
