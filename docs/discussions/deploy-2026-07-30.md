## D1 — Cloud Logging, which means the VM gets an identity

*Decided by Yi Xin, from three options put to them.*

The blocker was structural: the VM was created `--no-service-account
--no-scopes` on purpose (day-10 red team R-09 — an internet-facing VM running
third-party Python must not carry credentials its metadata server hands to
anything achieving RCE). No identity, no way to send anything anywhere.

Options put up:

1. **Minimal SA + Cloud Logging** — one role, `roles/logging.logWriter`.
   Readable without booting the VM, on the same timeline as the gate function's
   logs. Cost: the VM has an identity.
2. **Local disk only** — journald persistence plus a file. Zero new privilege,
   zero cost, but reading it means booting the VM (~$0.4 and 30 minutes) every
   time you want to know what happened.
3. Both.

A fourth option was considered and **discarded before it reached Yi Xin**: have
the VM report usage to the Cloud Function, which already logs, authenticated
with the `DEMO_GATE_KEY` they share. That key is handed to every visitor —
`main.py:314` embeds it in the demo URL as `?k=` — so any visitor could forge
usage records. Least privilege on paper, unauthenticated in practice.

**Chosen: option 1.** The point of the log is to know, from a laptop, days
later, whether a company actually used the demo. Option 2 fails that on its
first day.

The trade is recorded where it will be read (runbook §1 amended in place, §9 in
full): an RCE on the VM now yields a token that can do exactly one thing —
write log entries into this project. It cannot read data, start or stop
instances, or touch billing. The realistic abuse is log spam, bounded by the
$20 budget alert.

## D2 — Record the question text, not just counts

*Decided by Yi Xin, from three options.*

Counts and metadata would show *that* the demo was used and whether anything
tripped a fail-closed gate; only the text shows **what a recruiter cared
enough to ask**, which is the thing worth knowing before an interview. Accepted
consequence: a visitor's typed text is stored in the project's logs, with
30-day `_Default` retention.

Both lines are emitted only under `DEMO_PUBLIC=1`. Local `make demo` and the
test suite stay silent — the same rule every other day-10 fence follows, and the
reason a laptop never quietly accumulates a copy of every question asked while
developing.

## D3 — The entry point rides the log, not the request body

Only the client knows whether a question was clicked from the suggestion panel
or typed. The obvious move — add a `source` field to the `/query` body — would
have made the two entry points produce *different* requests, and day-10's red
team (2026-07-29 P2) established the opposite property on purpose: a click must
spend exactly what typing spends, checkable on the wire.

So the source label is logged client-side and never sent. The one thing that
does travel is a random per-turn id (`X-Demo-Turn`), drawn identically either
way, so the two log lines of a turn can be paired without leaking which button
produced it. The test asserts both POST bodies are byte-identical and only the
random header differs.

## D4 — What the red team changed

Full findings in the companion review; the two that mattered most were failures
of *honesty*, and both were confirmed by running the code rather than reading
it:

- The whole feature would have logged **nothing in production**. INFO is not
  enabled on the deployed uvicorn process; the tests only passed because
  `caplog` raised the level. Replaying uvicorn's logging config produced empty
  stderr. This is the second time this exact bug has appeared in this
  deployment (the trigger function, 2026-07-29).
- `retracted` was hard-coded false on the result path, while the engine
  retracts on *every* non-threshold refusal — the record would have reported a
  ~0% retraction rate for something that is not rare.

Both now have tests that fail against the previous behaviour. The remaining
findings (bounds-check orphans, exact version pinning, key-fingerprint TOFU,
proving ingestion works rather than checking a scope, structured `event` fields
instead of substring matching, `gate` vs `error_type`) were fixed in the same
session per the standing rule that red-team findings are fixed, not triaged.

## D5 — A second round, on the fixes

*Yi Xin: "红队指出的全修复。"*

Round 1's eleven fixes had been reviewed by nobody, so the same cross-host red
team was run again on the post-fix diff, told the fixes were unreviewed and to
look for defects **introduced** by them. It returned DO_NOT_MERGE again, with
nine findings — and the first one was that **the fix for F-01 had broken the fix
for F-09**: the handler added to make INFO emit also prefixed a timestamp, which
stops the Ops Agent parsing the line into `jsonPayload`, which is what the
documented readback query selects on. The feature would have shipped writing
records nobody could find. The test I wrote for F-01 split the line on `" INFO "`
— it asserted the bug into place.

The lesson worth keeping: **a fix aimed at one finding is a new, unreviewed
change**, and the most dangerous kind is the one that satisfies its finding
while voiding the feature. Two of round 2's three P1s are of exactly that shape
(the third, the blocked `beats.get()`, is a case round 1's fix simply could not
reach). Rounds are not ceremony.

## D6 — Where to stop

*Yi Xin: "不需要第三轮了，即使有问题也无伤大雅。核心的演示已经完整，现在只是锦上
添花。能捕捉到日志就行。"*

The implementer offered a third round and declined to judge whether it was
needed. Yi Xin's ruling draws the line on proportionality rather than on
residual risk: the demo's substance — retrieval, fail-closed generation,
citations — is already complete and reviewed; this change is telemetry about
that demo. A defect that survives here costs a missing log line. That is not
the same kind of risk as a fence that guards money or an answer that could be
wrong, and it does not earn a third pass.

Recorded because the *opposite* instinct — keep reviewing until nothing comes
back — would have been easy to justify from round 2's results, and would have
been wrong for this artefact.
