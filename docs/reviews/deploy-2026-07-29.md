## Part 1 — Findings

### P0

**R-01 — The cost fence is installed after the most fragile step; a failed
provision leaves a running, unfenced, billing VM.** `[external-only]`

`deploy/vm/provision.sh`: containers start, then `learnarken index` runs (model
download + feed), and only then are the systemd units installed and the watchdog
timer enabled. Every fence that makes this design affordable — 30-min idle
poweroff, 3 h hard cap — exists only after the step most likely to fail.

**Not hypothetical — this is what happened.** Provision died twice on
2026-07-29 (R-02, R-03). The VM stayed RUNNING for ~4.5 h at ~$0.36/h with no
watchdog installed at all, and would have run until a human noticed. The
implementer's own review had this class of risk pointed the wrong way (worrying
that the watchdog might kill a slow cold boot) and missed that during
provisioning the watchdog does not exist.

Fix: install the units and arm the watchdog **before** containers/index; suppress
only the *API-unreachable* strike during provisioning (sentinel under `/run`, so a
reboot re-arms it), never the uptime hard cap; add an `ERR`/`EXIT` trap so an
aborted provision leaves the fences armed.

### P1

**R-02 — `device: "mps"` is hardcoded; the stack cannot start on any non-Apple
host.** `[host-only]`

`embedding/providers.py:53,60` and `retrieval/hybrid.py:118`. Confirmed by real
crash on the VM after the 15 GB model download completed:
`RuntimeError: PyTorch is not linked with support for mps devices`. The entire
project was only ever runnable on the author's Mac. Fix: resolve the device at
runtime (cuda → mps → cpu) with an env override.

**R-03 — provision ran a Docker-dependent step as the user deliberately denied
Docker.** `[host-only]`

`provision.sh` ran `learnarken index` as `learnarken`, which is kept out of the
docker group on purpose (day10 #11); `vespa/store.py:130` shells out to
`docker cp`/`docker exec` on first deploy → EACCES → `set -e` abort → zero units
installed. Two correct decisions that were never run together. Fix: deploy the
Vespa application package as root inside provision before the index run.

**R-04 — The R-03 fix is first-run-only and hides schema drift.**
`[external-only]` — critique of the implementer's own fix.

The root deploy is guarded by "is `:8080` answering?", so on any re-run with a
changed application package the deploy is skipped, `docker cp` never clears
deleted files, and the corpus manifest can record a local schema digest while the
engine serves an older one. Fix: always deploy as root, clear the staging dir
first, and compare the deployed generation/digest rather than liveness.

**R-05 — The VLM second look spends money outside the spend fence.**
`[external-only]`, verified by the implementer.

`multimodal/second_look.py:35` allows `VLM_MAX_SAMPLES = 5`; `figure_second_look`
(`answer/figure_relook.py:55`) and the whole consensus path contain **no
reference to `DemoGuard`**. Only the main completion and its retry are debited
(`api/app.py:379,388`). A figure-targeted question therefore buys up to 5 VLM
calls while the quota records one. Same failure class as the Day 10 finding that
the guard did not cover the question path.

**R-06 — Cold boot can be killed by the fence meant to protect it.**
`[cross-validated]`

`run_demo_vm.sh` waits 120 s for the backend then `exit 1` → `Restart=on-failure`
loop; `idle_watchdog.py` `FAIL_LIMIT=10` powers off after 10 unreachable minutes,
first check `OnBootSec=5min`. An 8B embedding model loading from disk on 8 CPU
vCPUs can exceed both. Fix: derive both numbers from the **measured** cold boot
(INV-5) and add a boot grace keyed to uptime.

**R-07 — Streamlit binds `0.0.0.0` unconditionally while the guard fails *open*
outside public mode.** `[external-only]`, verified.

`run_demo_vm.sh:48-50` always binds publicly; `demo_guard.py:104-107` returns
`True` from `key_ok` whenever `DEMO_PUBLIC != "1"`, and `uploads_allowed()` is
likewise open. A typo in `demo.env`, or an operator running the script by hand to
debug, serves an ungated public app. Fix: refuse to bind publicly unless
`DEMO_PUBLIC=1` **and** a non-placeholder key is configured.

**R-08 — SSH is open to the internet on the demo VM.** `[external-only]`,
verified live.

The project's default `default-allow-ssh` (`0.0.0.0/0`, priority 65534) is
untouched by the runbook, so "only 8501 and 8110 are public" is false as
deployed. Fix: shadow it for the demo tag (deny tcp:22 at a lower priority
number) and allow SSH only from the operator IP and the IAP range.

### P2

**R-09 — Default Compute service account attached to a public VM.**
`[external-only]` — **severity corrected down from the external P0 by live
verification**: the default SA
`439335822959-compute@developer.gserviceaccount.com` holds **no project IAM role**
in this project, so a stolen metadata token grants effectively nothing. The
finding stands as hardening, not as a live escalation path. Fix (cheap):
`--no-service-account --no-scopes`.

**R-10 — Documented standing cost contradicts the configuration the same
document creates.** `[host-only]` `DEPLOY-GUIDE.zh.md:29,220` state ~$4/month
(a `pd-standard` figure) while Step 1 of the same guide creates 100 GB
`pd-balanced` ≈ $10/month. An honesty defect in a document whose purpose is cost
transparency.

**R-11 — The runbook makes the VM fetch `provision.sh` from `main`.**
`[host-only]` Any fix not pushed to `main` is not the script that runs. The two
fixes made on 2026-07-29 were live only because they were `scp`-ed by hand.

**R-12 — The ready email hands out the shared gate key.** `[external-only]`
`trigger/main.py:138-140` mails `demo_url`, which embeds `DEMO_GATE_KEY`. Mail
is stored, forwarded and indexed. Fix: mail the token URL, never the keyed URL.

**R-13 — Secrets are passed as `--set-env-vars` and staged through `/tmp`.**
`[external-only]` `runbook.md:70-72,114-119`. Shell history, function env
visibility, and a comma inside `TOKENS_JSON` all bite. Fix: `--env-vars-file`
(or Secret Manager), and `scp` to a mode-600 path rather than `/tmp`.

**R-14 — "ready" does not mean answerable.** `[external-only]` /
`[host-only]` (implementer's D6, same root). `/demo/status` checks Vespa, Neo4j,
LLM config and threshold; it does not check that the gate key is configured, and
no model is warmed until the first question — so the page can say ready while the
first visitor waits through a cold model load, or gets 403 on every query.

**R-15 — Trigger rate limit is per function instance.** `[external-only]`
`main.py:55-58` in-memory + `--max-instances=2` ⇒ the "once per hour" limit is
per instance and forgotten on cold start. Documented as best-effort, but the
document overstates it.

**R-16 — Supply chain is looser than a live public VM warrants.**
`[external-only]` Mutable Docker tags (`provision.sh:17-18`), `uv` installed by
piping a remote script, no `uv sync --locked`, compatible-range function
requirements.

### P3

**R-17 — Neo4j readiness is checked unauthenticated against a hardcoded
password.** `[external-only]` — **severity corrected down from the external P1**:
`provision.sh:62-65` hardcodes `neo4j/learnarken` and the health check is an
unauthenticated `curl :7474`, but the deployed `.env` password *is* `learnarken`,
so nothing is broken today. Latent: any `.env` password change makes provisioning
report healthy and then fail with 401.

**R-18 — The public shim leaks usage timing and is unbounded.**
`[external-only]` `status_shim.py` forwards the full backend payload
(`started_at`, `last_business_activity`, `idle_seconds`) to anyone with the IP,
runs an unbounded `ThreadingHTTPServer`, releases its lock before the backend
fetch (no single-flight), and logs nothing.

**R-19 — Observability gaps at exactly the failure points that matter.**
`[external-only]` The watchdog ignores the result of `systemctl poweroff`
(`idle_watchdog.py:86-88`); provision has no phase log; the shim is silent.

**R-20 — Runbook paper cuts.** `[external-only]` Hardcoded
`GCP_ZONE=us-central1-a` in the function deploy while `$ZONE` is exported
elsewhere; the API-enablement step omits APIs a genuinely fresh project needs.

## Part 1b — Round 2: red team of the fix batch

> Same cross-host routing (Codex). Occasion: all 20 round-1 findings were fixed
> the same day and the deployment then ran for real. **This round reviews the
> fixes themselves** — three of them had already spawned fresh failures visible
> only on a real machine (S-04a/b/c below). External verdict: **DO_NOT_MERGE**.
> All 15 were fixed; the suite is 680 green.

### P1

**S-01 — The cost fence still was not armed *first*.** `[external-only]` The
watchdog needs the repo cloned, so `apt-get` and `git clone` still ran unfenced —
R-01 again, moved earlier in the script. Fixed: a `systemd-run --on-active=3h`
transient poweroff timer is now the first command, needing nothing from the repo,
and is stopped once the real watchdog is armed.

**S-02 — Warm-up failure was swallowed forever.** `[external-only]` One transient
exception left `_models_warm` false permanently while the process stayed alive;
`Restart=on-failure` never participates, so the VM would burn to the idle fence
and never become usable. Fixed: bounded retry (3 × 20 s) then a loud error.

**S-03 — The warm thread could double-load the 8B model.** `[external-only]`
`functools.cache` memoizes a result; it does not serialize the call. The new warm
thread plus a concurrent `/query` could each build a fp32 8B model (~32 GB) on a
64 GB VM. `_RERANKER_CACHE` had no lock at all. Fixed: single-flight locks with
double-checked insert on both.

**S-04 — Pinning the script did not pin the application.** `[external-only]`
The runbook pinned `provision.sh` to a commit, but the script cloned a branch —
so the deployed app could be a different commit than the reviewed script. Fixed:
`provision.sh <url> [<sha>]` does `git checkout --detach`, and warns loudly when
no SHA is given.

**S-04a/b/c — Three follow-on failures from the R-04 fix, found by running it.**
`[host-only]` (a) `docker inspect` succeeds for a *stopped* container, so after a
reboot `inspect || run` started nothing and provisioning waited on the health of
two exited containers; (b) `docker exec` defaults to the image's unprivileged
user and could not delete the root-owned files `docker cp` had left; (c) the
health wait fell through silently on timeout. All three fixed.

### P2

**S-05 — Digest pinning was inert for existing containers.** `[external-only]`
`start_or_run` only started what already existed, so a container created from the
old mutable tag would be restarted and the run would "pass" while serving the
unpinned image. Fixed: compare the container's image id against the pinned
image's and recreate on mismatch. Covered by behavioural shell tests.

**S-06 — The shim's cache was stamped before the fetch.** `[external-only]` A
probe slower than the 3 s TTL was born expired, so every waiting poller took the
lock and made its own 5 s backend call in turn. Fixed: stamp after the fetch.

**S-07 — The start handler rate-limited before knowing a start was needed.**
`[external-only]` A double click or a lost response turned an already-running
stack into a 429. Also, `instances.start` was uncaught — and a zone stockout is a
real observed outcome. Fixed: read state first, return `starting` when already
up, limit only a real start, and return 503 with a retry message on failure.

**S-08 — The page hid the two new readiness gates.** `[external-only]` The page
could sit in `starting` with every visible check green. Fixed: labels for
`gate_key` and `models_warm`.

**S-09 — The Cloud Function's dependencies were the last unpinned surface.**
`[external-only]` Fixed: exact pins.

**S-10 — The two operator documents diverged.** `[external-only]` The Chinese
guide still staged secrets through `/tmp` and enabled three APIs; both still set
SMTP placeholders after email was made optional. Fixed in both — the sibling
operator path is exactly where a fix goes stale.

**S-11 — Machine-type evidence was inconsistent.** `[cross-validated]` The docs
create `e2-highmem-8` while the deployed VM is `c3-highmem-8` (forced by a
us-central1-a stockout on 2026-07-29) and every measured constant was measured on
`c3`. Fixed: both documents now create `c3-highmem-8` and state the cost delta
(~$0.53/h vs ~$0.36/h; ~$0.16 per session) and the re-measure rule.

### P3

**S-12 — Provisioning had no concurrency ownership.** `[external-only]` Two runs
would race and each one's EXIT trap would clear the other's sentinel. Fixed:
`flock`.

**S-13 — Quota exhaustion was reported as a figure-evidence refusal.**
`[external-only]` Fixed: a `QUOTA_EXHAUSTED` marker and a `quota_exhausted` flag
in the trace.

**S-14 — Several new tests were text assertions that would pass with the defect
present.** `[external-only]` A fair hit. Fixed: `start_or_run` is now exercised
for real against fake `docker` binaries (create / start / recreate-on-mismatch).

## Part 1c — Concurrency and shutdown drills (measured, 2026-07-29)

> Run at Yi Xin's request, after both review rounds. Every row is a measurement
> on the deployed VM, not an argument from the code.

**Two people click the link at the same time — is there a lock?**
No application-level lock, and none is needed: `instances.start` is idempotent
at GCE. Two concurrent starts against the same VM both returned success and
produced **one** machine with **one** `lastStartTimestamp`. The code's race
window (both requests read `TERMINATED` before either starts) therefore has no
cost or correctness consequence. Deliberately not fixed with distributed state —
Firestore would add a failure surface to remove a race that idempotency already
absorbs. **Open for adjudication.**

**One person clicks twice quickly — is the second ignored?**
Yes, and this only became true in round 2 (S-07). Already starting or running →
`{"state": "starting"}`, no second start call. Still stopped and within the
5-minute global floor, or the token's hour → 429 with the remaining seconds.
Before S-07 the limit was applied *before* reading instance state, so a repeat
click on an already-booting stack showed the visitor an error.

**Two visitors at once, after it is up?**

| Load | Result |
| --- | --- |
| 1 question | 10.3 s |
| 2 concurrent | both answered, 4 citations each, 15.1 s / 18.8 s |
| 3 concurrent | two answered (13.7 / 13.9 s); the third refused in **0.01 s** by the concurrency fence |

`DEMO_MAX_CONCURRENCY=2` is a deliberate spend fence: on CPU a third concurrent
query only slows everyone down, so it refuses immediately with a reason.

**S-15 — Found by that drill: the reranker mutated shared state per call.**
`[host-only]` The `CrossEncoderReranker` wrapper was cached and its `top_n`
reassigned on every call — shared mutable state on a path two visitors enter at
once, so one query could rerank to the other's depth. Fixed: cache the model,
build the cheap wrapper per call.

**S-16 — Found by that drill: warming ran in every test process.**
`[host-only]` `create_app()` started the warm thread unconditionally, so every
test that builds an app began a background multi-GB model load — noisy locally
(a PyTorch internal assert at interpreter shutdown) and a real failure in CI,
which has no model cache. Fixed: warm only when `DEMO_PUBLIC=1`; `models_warm`
reports True outside public mode, where models stay lazy. Verified against a
clean environment (`mv .env .env.bak`): 680 green.

**Does the idle shutdown actually reclaim the machine?**
**Yes — measured, not inferred.** Previously only the "keep running" branch had
been exercised. Drill: `IDLE_LIMIT_S` was temporarily lowered to 180 s **on the
VM only, that constant alone** — timer, watchdog script, `systemctl poweroff`
and the GCE state transition all real. The instance reached `TERMINATED` on its
own. The threshold was then restored to `30 * 60` and diffed against the repo
constants to confirm byte equality; leaving 180 s in place would have powered the
machine off while a recruiter was reading an answer.

## Part 1d — Step 6-8 go-live findings (2026-07-29)

**S-17 — The interest signal was written and silently discarded.**
`[host-only]`, found by reading the deployed function's own logs rather than
trusting the code. `logger.info("demo link opened by recipient=...")` is the
**only** channel that answers "who opened the link" now that email is off — and
Python's default root level is WARNING, with a last-resort handler that drops
anything below it. Rejected requests (`logger.warning`) appeared; every click
record did not. Fixed: `logging.basicConfig(level=logging.INFO)` plus an explicit
logger level, redeployed, and verified live — two channel labels now appear
distinctly, still with only the token's hash prefix, never the raw token.

**S-18 — Removing the VM's service account broke the function build.**
`[host-only]` Cloud Functions gen2 builds with the *Compute Engine default*
service account, which this project deliberately grants no roles (R-09). The
first deploy failed with a build-permission error. Fixed without widening the
shared default SA: a dedicated `learnarken-build` service account holding only
`roles/cloudbuild.builds.builder`, passed via `--build-service-account`. Two
least-privilege decisions that only collide when actually run — the same shape
as R-03.

### P2

**S-20 — One-click Ask had no in-flight guard; an impatient visitor could bill
several generations nobody would ever see.** `[cross-validated]`

Streamlit greys out `st.chat_input` while a run executes, but **not buttons**. A
click during a slow generation aborts the running script *after* its LLM call
was already issued, then starts another. Two tabs on the same `?k=` can also
occupy both `DEMO_MAX_CONCURRENCY` slots.

Fixed: a question is now accepted on one run (`st.session_state.pending_question`
+ `st.rerun()`) and asked on the next, so the panel that renders on the spending
run renders its buttons `disabled`. `pending_question` is cleared in a `finally`,
so a torn-down run can never re-ask and re-bill. The client cannot fence a second
browser tab — the backend semaphore and the per-boot call cap remain the real
fences, and that limit is stated in the code comment rather than papered over.

**S-21 — "Clicking equals typing" was asserted by a regex over the source, not by
behaviour.** `[external-only]`

`source.count('f"{API_BASE}/query"') == 1` would still pass if a future edit
added `requests.post(API_BASE + "/query", ...)` without `_demo_headers()`.

Fixed: the query call site is extracted to `ask_backend(question, entry)` — the
one path both entry points take — and the test now executes the *shipped*
function against a fake `requests`, asserting exactly one POST, to `/query`,
carrying `X-Demo-Key`.

### P3

**S-22 — The provenance test globbed `eval/golden/*.jsonl`, which includes
un-adjudicated `*.candidates.jsonl` rows.** `[external-only]`
Fixed: the four reviewed sets are named explicitly (day4, day8-adversarial,
day11-multihop, day12-multimodal); a candidates row can no longer reach the
public demo with the test still green.

**S-23 — Group notes read as outcome promises ("watch for…", "…is stopped") for a
non-deterministic generator.** `[external-only]`
Fixed: every note is now a question ("probe: … does a named gate fire — or a
guess?"), and the panel caption states outright that the same question can land
differently twice, with the gate name and trace ID as the way to tell which path
it took.

**S-24 — Group names and notes reach `st.markdown`, which renders links.**
`[external-only]`
Static literals today, so not a live injection bug; the risk is a future edit
sourcing them from document- or eval-derived text. Fixed by making the guard
explicit rather than accidental: a test reads the table through
`ast.literal_eval`, which fails the moment it is built from anything computed or
loaded. Question text was never at risk — `st.code` escapes.

**S-25 — `pyproject` floor is `streamlit>=1.41` while `uv.lock` pins 1.59.2.**
`[external-only]`
No change needed, verified rather than assumed: `provision.sh:99` installs with
`uv sync --group demo --locked`, so the VM deploys the locked 1.59.2 exactly.
Codex separately confirmed `st.columns(vertical_alignment=…)`,
`st.expander(expanded=…)` and `st.code(language=None)` all exist at the 1.41
floor, so the declared range is honest either way.
