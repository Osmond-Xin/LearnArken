## Part 1 — Findings

### P1

**F-01 — The access log would have recorded nothing in production.**
`[external-only]`

`src/learnarken/api/app.py`: the record was written with `logger.info(...)`, but
nothing in the deployed process enables INFO. Python's root level is WARNING,
`uvicorn` configures only its own loggers, and the last-resort handler drops
anything below WARNING. The tests passed because `caplog.at_level` raised the
level for them.

**Verified, not argued.** Replaying uvicorn's `LOGGING_CONFIG` and calling
`logger.info` produced empty stderr, with the `learnarken` logger at effective
level 30. The feature would have shipped, gone green, and recorded zero visits —
the same failure the trigger function hit on 2026-07-29, where the click record
was written and silently discarded.

Fixed: `enable_public_access_log()` attaches a stderr handler and sets INFO on
the `learnarken` logger, called from `create_app()` in public mode only. Pinned
by `test_info_actually_reaches_stderr_in_public_mode`, which reads captured
stderr rather than `caplog`, and by a second test that re-entry adds no
duplicate handler.

**F-02 — `retracted` was hard-coded false on the path where retraction is the
norm.** `[external-only]`

`answer/engine.py` emits a `retract` event on **every** non-threshold refusal —
citation-validation, llm, llm-contract. The result path logged
`retracted=False` unconditionally, so a visitor who watched generated text
appear and then be withdrawn produced a record indistinguishable from a
threshold refusal, where nothing was ever generated. Retraction rate read off
these logs would have been ~0 against a true rate that the day-8/day-13 work
shows is not rare.

Fixed: the SSE loop tracks `retract` events (including the transport-failure
retraction the API emits itself) and the record reports it. Pinned from both
sides: `test_a_refusal_that_withdrew_text_says_so` and
`test_a_threshold_refusal_did_not_retract`.

**F-03 — A visitor who closes the tab mid-answer leaves no record at all.**
`[external-only]`

The terminal record was written after the SSE generator's loop. When the client
disconnects, Starlette closes the generator, `GeneratorExit` is raised at the
`yield`, and nothing after the loop runs — while the worker thread keeps its LLM
slot and finishes the billed generation. The abandoned query is precisely the
one that costs money and reaches nobody, and it was the one guaranteed to go
unlogged.

Fixed: a `finally` writes an `outcome: "aborted"` record, guarded so a normal
ending is never double-counted. Pinned by
`test_an_abandoned_stream_is_still_recorded`, which drives the shipped generator
and calls `.close()` on it — `TestClient` drains the response instead of hanging
up, so the first version of this test passed against the bug.

### P2

**F-04 — A question outside 3–500 characters logged an entry with no
outcome.** `[external-only]`

The client logged `demo_entry` before the POST; the backend answered 422 without
reaching the query path. The result was a half-turn in the log that reads like a
question that vanished. Fixed: the client checks the bounds it already advertises
in its placeholder, tells the visitor, and does not log or send.

**F-05 — The whole journal ships, and `?k=` could ride along.**
`[cross-validated]`

`systemd_journald` collects everything on the box, not just the two event lines
— including any component that logs request URLs, which carry the shared
`DEMO_GATE_KEY` as `?k=`.

**Measured rather than assumed**: the shipped Streamlit was run locally and hit
with `/?k=SUPERSECRETKEY123` (200) and `/nope?k=…` (404). It emitted **no**
request log lines at all, so the key does not reach the journal by that route.
Whole-journal collection is kept deliberately — a demo that broke in front of a
recruiter must be diagnosable afterwards — and the runbook now states what
ships, what it costs, and that retention is 30 days.

**F-06 — `logging.logWriter` is write-only, but it still lets a compromised VM
forge and flood.** `[cross-validated]`

Accepted as the price of the record, and now stated where it can be acted on:
the runbook says in as many words that these lines are **telemetry, not audit**
(Cloud Audit Logs remain the trustworthy half), that ingestion is free to
50 GiB/month, and that the $20 budget alert is the only fence on log-volume
abuse.

**F-07 — The agent was major-version-pinned, and the signing key was fetched
with no verification.** `[cross-validated]`

`google-cloud-ops-agent-bookworm-2` still lets an unattended upgrade swap the
agent under a live demo, and `curl | gpg --dearmor` trusts whatever arrives.
Fixed: the exact candidate version is resolved, installed and `apt-mark hold`-ed
(and echoed), and the key fingerprint is recorded on first install and compared
on every later run, refusing to continue if it ever changes. A fingerprint
written from the implementer's memory would have been worse than no check —
trust-on-first-use plus a hard compare is what can be honestly implemented here.

**F-08 — The installer checked the scope, which does not prove ingestion
works.** `[external-only]`

A scope passes even when the IAM role was never granted or was later revoked;
the agent then spends the whole boot retrying 403s while the operator believes
visits are being recorded. Fixed: after restart the installer emits a marker,
waits, greps the agent's own journal for `PermissionDenied|403|unauthenticated`
and fails loudly, then prints the exact `gcloud logging read` for the operator
to confirm from outside — the VM cannot read its own logs back, deliberately.

### P3

**F-09 — Substring readback was forgeable and ambiguous.** `[external-only]`

`textPayload:"demo query"` matches any question containing that phrase — a
visitor could type it. Fixed: each message is now exactly one JSON object
carrying `"event": "demo_query"` / `"demo_entry"`, which the Ops Agent parses
into `jsonPayload`, and both runbooks select on `jsonPayload.event`.

**F-10 — `gate` was overloaded with exception type names.** `[external-only]`

A refusal gate and a Python exception class are different facts sharing one
field. Fixed: `gate` is refusal-only, `error_type` carries the exception.

**F-11 — Nothing linked the client's entry line to the backend's query
line.** `[external-only]`

With two visitors on one machine, "which record is the suggestion click" was
guesswork. Fixed: a random per-turn id, sent as `X-Demo-Turn` and logged by both
sides. It is drawn identically for typed and clicked questions, so the day-10
property that a click puts the same bytes on the wire as typing is preserved —
and now tested directly, by asserting the two POST bodies are byte-identical
while only the random turn header differs.

### Host-side pass — no additional findings beyond the above

The implementer's independent pass raised log injection (already handled by JSON
encoding, and pinned by a test that feeds a newline-and-forged-record question),
unbounded question length (capped at the wire limit, re-applied in the helper so
a direct call cannot bypass it), and the visitor-controlled `X-Demo-Turn` header
(bounded to 16 characters and stripped to `[A-Za-z0-9_-]`, pinned by a test).

## Part 1b — Round 2, on the fixes themselves

> Same routing (Codex, cross-host), run after round 1's eleven fixes were in
> place, told explicitly that the fixes were unreviewed and to look for defects
> **introduced by them**. Verdict again: **DO_NOT_MERGE**. Nine findings, all
> fixed. Requested by Yi Xin ("红队指出的全修复", 2026-07-30).

### P1

**R2-01 — The round-1 fix for F-01 broke the round-1 fix for F-09.**
`[external-only]`

The handler added to make INFO come out formatted the record as
`"%(asctime)s %(levelname)s %(message)s"`. The message therefore is no longer
*only* JSON, the Ops Agent does not parse it into `jsonPayload`, and the
readback query written into both runbooks —
`jsonPayload.event="demo_query"` — would have matched **nothing** in
production. Every test stayed green, because the test I wrote for F-01 did
`.split(" INFO ", 1)[1]`: it asserted the bug.

This is the same class of failure as F-01 itself, one layer up — a fix that
satisfies the finding it was aimed at while quietly voiding the feature.

Fixed: a dedicated `learnarken.demo_access` logger, `%(message)s` formatter,
`propagate = False` (a parent handler would emit a second, prefixed copy).
`test_the_emitted_line_is_nothing_but_json` now asserts
`json.loads(stderr.strip())` — nothing before or after the object.

**R2-02 — The abort net cannot fire while the generator is blocked.**
`[external-only]`

`beats.get()` blocks with no timeout. A sync generator suspended there cannot be
interrupted: Starlette can only raise `GeneratorExit` when the generator is next
resumed. So the case that motivated F-03 in its worst form — the LLM stalls
before the first token, the visitor gives up and closes the tab — held an LLM
slot with no record written at all.

Fixed: `beats.get(timeout=15)` and an SSE comment frame on timeout. A comment is
ignored by any conforming client (the demo's own parser reads only `event:` and
`data:` lines, asserted by a test), and sending it against a departed client is
what surfaces the disconnect. `test_a_stalled_generation_still_notices_the_visitor_left`
would hang rather than fail without this.

**R2-03 — Provisioning could still serve a public demo with no log shipper.**
`[external-only]`

The `provision.sh` call swallowed every failure with a warning. Fixed with a
distinction the previous version could not make: the installer exits **78** when
the VM carries no service account (a deliberate no-identity build — how this VM
ran until today) and provisioning continues; any other non-zero exit means an
identity *was* attached, so logging is intended, and provisioning now fails
rather than producing a public demo that records nothing.

### P2

**R2-04 — The outcome was recorded before its own frame was delivered.**
`[external-only]`

`record()` ran before `yield`. A visitor disconnecting during the final frame
left a record saying `answered` for an answer they never received, and the
once-only guard made it uncorrectable. Fixed: the terminal outcome is held in a
local and written only after `yield done` returns; a disconnect before that
falls through to `aborted`. Pinned by
`test_an_outcome_is_recorded_only_once_delivered`.

**R2-05 — `saw_retract` was set before the retraction was delivered.**
`[external-only]`

Same shape, one field down: a retraction the visitor never received was recorded
as one they saw. Fixed by setting the flag after the yield returns.

**R2-06 — The client-side bounds check left the server side unaudited.**
`[external-only]`

A 422 never reaches `/query`, so anything reaching the backend by another route
still produced an entry with no outcome. Fixed: a `RequestValidationError`
handler logs `outcome: "rejected"`. Registered unconditionally and gated inside
`_log_query_access` — gating at registration would have bound the behaviour to
whatever `GUARD.public` was when the app object was built, which is what the
first attempt did, and the test caught it.

**R2-07 — Re-runs did not enforce the pinned agent version, and the hold was
never re-applied.** `[external-only]`

Fixed: the version is recorded on first install and enforced on every later run
(refusing, with the deliberate upgrade path printed), and `apt-mark hold` is
re-applied every run. The trade — a held package stops receiving security fixes
— is stated in the script next to the upgrade command.

**R2-08 — The runbook told the operator to run a `learnarken`-owned file as
root.** `[cross-validated]`

Anything that compromised the VM as `learnarken` could rewrite
`install_ops_agent.sh` and wait for the next `sudo bash` — a privilege
escalation handed over by the runbook itself. Fixed: §9c asserts `HEAD` is the
reviewed SHA and the tree is clean, then installs the script to a root-owned
path and runs that.

### P3

**R2-09 — `X-Demo-Turn` is sanitized but still caller-chosen.**
`[external-only]`

HMAC-signing it would be theatre: the visitor holds `DEMO_GATE_KEY`, so they
could sign one too. The honest fix is to stop the record implying otherwise —
the field is now `turn_claimed`, and the runbook already frames these lines as
telemetry rather than audit. The broad-logger half of this finding is fixed by
R2-01's dedicated logger.
